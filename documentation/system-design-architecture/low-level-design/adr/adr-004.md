
ADR-004: ESTRATÉGIA MULTI-TENANT

Status: Aceito
Data: 26-10-2026
Contexto: Objetivo final é virar mini-SaaS vendável no Brasil (R$) e Europa (€). Critério CS05: cadastrar 2ª empresa (AgroTrafo) sem refazer BD. Precisa decidir como isolar dados entre LWEI e outras empresas.

Decisão: Usar Shared Database, Shared Schema com coluna empresaId obrigatória em todas as tabelas + TenantGuard + RLS opcional

Justificativa:
1. 3 modelos avaliados: a) Database por tenant b) Schema por tenant c) Shared Database Shared Schema com empresaId.
2. Por que escolhemos Shared Database Shared Schema: Custo zero no MVP (1 BD Supabase free tier serve todas as empresas), migração Prisma roda 1 vez para todas, código mais simples (sempre WHERE empresaId). Database por tenant precisaria criar BD novo por cliente, custo inviável. Schema por tenant precisaria de migrations por schema, complexo para 1 dev.
3. empresaId em TUDO: Toda tabela (empresas, users, servicos, clientes_portfolio, membros_equipa, projetos, project_members, custos) terá empresaId UUID + FK para tabela empresas + índice. Prisma middleware garante que se esquecer WHERE, joga erro.
4. TenantGuard no NestJS: Guard global extrai empresaId do JWT e seta em Request. Todos Services recebem empresaId e nunca confiam em param vindo do frontend. Evita ataque mudando empresaId na URL.
5. Reforço com RLS no Supabase (opcional no MVP): Política: USING (empresaId = http://auth.jwt() ->> 'empresaId'). Segunda camada de segurança caso bug no NestJS.

Consequências:
Positivas: CS05 atendido, custo zero, simples de implementar, escala até ∼100 empresas sem problema no PSQL.
Negativas: Se uma empresa crescer muito, pode afetar performance das outras. Mitigação: Índices por empresaId + paginação + cache Redis por empresaId. Para > 100 empresas, migrar para schema por tenant na Fase 3.
Alternativas consideradas: Database por tenant (descartado por custo), Schema por tenant (descartado por complexidade para 1 dev no prazo Dezembro 2026).
