
ADR-005: ESTRATÉGIA DE ARMAZENAMENTO DE FICHEIROS

Status: Aceito
Data: 26-10-2026
Contexto: Precisamos guardar logos de clientes de portfólio, fotos de projetos, relatórios PDF para área do cliente. Requisito RN05: limite 5MB e compressão. Risco 2: upload pesado derruba servidor.

Decisão: Usar Supabase Storage (S3 compatível) + fila BullMQ image:compress com sharp

Justificativa:
1. Não salvar no PostgreSQL como bytea: PSQL ficaria gigante, lento e backup caro. File deve ficar em Object Storage.
2. Supabase Storage vs S3 AWS: Supabase já é nosso PSQL (mesmo projeto), free tier 1GB, tem CDN, políticas RLS por bucket. S3 AWS cobra e precisa configurar IAM. Custo zero no MVP.
3. Limite 5MB na API: Pipe FileSizeValidationPipe no NestJS barra antes de chegar no Storage. Retorna 413 Payload Too Large.
4. Compressão assíncrona com BullMQ: Fluxo: 1) Cliente faz upload -> 2) API salva arquivo original no bucket temp/ -> 3) API cria job bull:image:compress com { filePath, empresaId } -> 4) Worker baixa, comprime com sharp para webp 80% qualidade max 1200px, salva em public/ -> 5) Atualiza URL no PSQL. Resposta da API fica < 200ms, não derruba servidor.
5. Buckets separados por empresaId: /{empresaId}/logos/, /{empresaId}/projetos/, /{empresaId}/relatorios/. Reforça isolamento multi-tenant + facilita deletar empresa inteira se precisar.

Consequências:
Positivas: Performance, custo zero, isolamento, sem derrubar API.
Negativas: Precisa de worker BullMQ rodando. Mitigação: Mesmo processo NestJS roda worker em modo híbrido no MVP (não precisa de servidor extra).
Alternativas consideradas: Salvar base64 no PSQL (descartado por performance), Cloudinary (descartado por custo), S3 AWS puro (descartado por custo e complexidade no MVP).
