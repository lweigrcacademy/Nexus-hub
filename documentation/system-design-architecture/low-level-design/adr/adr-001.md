
ADR-001: USO DE NESTJS COMO BACKEND FRAMEWORK

*Status:* Aprovado
*Data:* 28/10/2026
*Contexto:* Precisamos de um backend para suportar milhares de portfólios multi-tenant, com autenticação, rate limit, validação e arquitetura escalável para 1 dev solo mas preparada para equipe. Alternativas: Express puro, Fastify puro, AdonisJS.

*Decisão:* Usar NestJS com Clean Architecture nativa (Controllers -> Services -> Repositories).

*Por quê BigTech:*
- NestJS já vem com injeção de dependência, Guards para multi-tenant (ownerId), Interceptors para cache Redis, Pipes para validação Zod/Class-validator. Express puro teríamos que montar tudo na mão.
- Monolito modular: cada domínio é um Module (AuthModule, PortfolioModule, ProjetosModule). No futuro podemos extrair um módulo para microserviço sem reescrever.
- Suporte nativo a TypeORM, Redis, JWT.

*Consequências:*
- Positivo: Código padronizado, fácil de onboardar outro dev.
- Negativo: Curva de aprendizado maior que Express, boilerplate inicial.
- Mitigação: Usar `nest g module/resource` para acelerar.

*Alternativas Rejeitadas:* Express puro (sem padrão), Fastify (performático mas menos ecossistema de Guards).
